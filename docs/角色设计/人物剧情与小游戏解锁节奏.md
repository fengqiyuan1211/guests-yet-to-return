# 人物剧情与小游戏解锁节奏

更新：2026-10-14。本说明区分本次已实现内容与后续建议。

## 1. 本次调整

小游戏可以在人物故事中途开放。玩家先认识客人、理解眼前的处境，再一起做一件事；之后客人仍会回来，讲述事情的进展。

| 客人 | 正式邀请条件 | 叙事安排 | 后续剧情 |
| --- | --- | --- | --- |
| 米洛 | 完成第 2 轮剧情；不额外要求满意招待 | 提起罗恩用渡河题教他检查路线，拿出木偶与草稿，邀请玩家试摆 | 第 3—5 轮继续地图补救与返乡线；第 5 轮呼应草稿 |
| 老霍克 | 完成第 3 轮剧情；不额外要求满意招待 | 讲完风沙中的经历后，邀请玩家用货棚草图复盘备料与通路 | 第 4—5 轮继续退稿与纪念牌线；第 5 轮才揭晓车夫姓名 |
| 艾达 | 保持第 5 轮剧情 + 2 次满意招待 | 给自己留下时间之后，才邀请玩家修自己的怀表 | 本次未调整 |
| 小线 | 保持原有五章与五杯评分判定 | 保留完整的童年回忆积累 | 本次未调整 |

这里的“轮”是剧情章节，不是实际制作杯数。最后的口味提示也要读完并确认继续，该章才算完成。米洛与老霍克即使没有累计高评分酒，也能在相应剧情节点收到邀请；调酒评分、满意度、收益仍正常计算。

## 2. 玩家能看到什么

1. 对话自然出现小游戏邀请，不需要等到所有故事结束。
2. 手帐显示该游戏自己的真实条件与当前进度，不再统一写“五章 + 两次满意招待”。
3. “开始游戏”放在解锁状态下方；纪念物、邀请原话与奖励说明排列在后面，避免长说明把入口挤出首屏。
4. 提前解锁的游戏注明后续来访故事仍会继续。
5. 酒馆状态栏汇总当前客人的已解锁游戏数量，为以后多个邀请预留显示方式。
6. 老霍克小游戏使用“车夫”等称呼，避免第 3 轮就透露第 5 轮才查清的姓名。纪念物说明留出姓名空位，不声称已经完成整个故事。

米洛渡河与老霍克推箱子的核心玩法不因解锁提前而变更。保留现有画风、工作台、自由调酒和手帐功能。

## 3. 后台数据如何对齐

### 条件来源

`data/guest_activities.json` 使用“客人 ID → 小游戏 ID”的结构；每个小游戏独立配置：

| 字段 | 用途 |
| --- | --- |
| `guest_id` | 关联角色剧情与招待记录 |
| `required_chapters` | 已完成章节门槛 |
| `required_satisfied` | 满意招待次数；0 表示无此额外门槛 |
| `route` | 进入对应 Godot 页面 |
| `keepsake`、`invitation` | 正式邀请后的纪念物与文字 |
| `reward_recipe_id`、`reward_inspiration` | 该小游戏正式首通奖励 |
| `demo_unlocked` | 内测体验入口，不等同于正式剧情邀请 |

`GuestActivities.progress(activity_id)` 统一读取条件、实际章节数、满意招待数，输出 `eligible`、`unlocked`、纪念物与领奖记录。`requirement_text()` 从相同条件生成手帐和演示结果页文字，避免界面与实际判断各写一套数字。

满意招待沿用既有口径：成功结算、对应角色、评分达到 70，按来访 ID 去重；兼容新旧两种结算记录。自由调酒不冒充剧情招待。此口径仍用于艾达等需要满意招待的游戏。

### 邀请、纪念物与首通奖励

三者不能混为同一次发奖：

- 条件达成：保存该小游戏的正式邀请；手帐展示相应纪念物。
- 正式首次通关：授予该小游戏的配方与研发灵感，现有三款配置均为 3 点。
- 重玩、重复结算、演示模式：不重复授予首通奖励。

邀请与奖励记录以 `activity_id` 区分。一个客人的第一款游戏领奖，不应占用其第二款游戏的领奖资格。

### 保存与旧存档

`GuestActivities.reconcile()` 在启动和相关剧情、招待记录变化后检查条件。先通过工作台共享库存账本的原子写入保存活动邀请，再同步 `StoryDialogue.unlock_activity()` 的手帐标记。

- 第一处保存失败：不发邀请、不改变剧情标记，可以重试。
- 邀请已保存但手帐同步失败：保留有效邀请；重试补上手帐标记。
- 已达到新门槛的旧存档：自动补齐邀请，不要求重读前几章。
- 已解锁、已通关、已领取奖励的存档：保留记录，不重复领奖。
- 章节 ID、对白节点 ID、小游戏 ID 保持稳定，不重置未读完的剧情。
- 历史对话仍保留玩家当时读到的内容；更新文案不会伪造或重复写入旧对话。

本次只调整解锁条件与相关文字，不在迁移时增加金币、原料或研发灵感。

## 4. 以后一个角色有多个小游戏

当前数据与手帐支持一个角色挂多个活动；目前仍只有已经实现的这些游戏，没有凭空新增玩法。

添加第二款时需要：

1. 给新游戏新的稳定 `activity_id`，不要复用旧游戏 ID。
2. 在同一角色下配置它自己的解锁条件、邀请、纪念物与奖励。
3. 实现并注册新路由、规则和存档校验；仅添加 JSON 不会自动生成可玩的小游戏。
4. 给对应章节写自然邀请，并核对会不会透露后续剧情。
5. 验证两款游戏进度、奖励、重玩和旧存档恢复相互独立。

目前条件只实现“章节数 + 满意招待数”。特定剧情选择、前一小游戏通关、指定物品等条件，需后续明确设计并扩展规则，不应假定已经支持。

## 5. 后续建议（尚未实现）

- **解锁后有一句回应。** 客人下次来访时，根据是否玩过或通关说一句不同的话，再继续主线。需要新增条件对白，不能直接写死“你已经通关”。
- **第二款游戏承担新阶段。** 米洛以后可以从渡河练习发展到地图连路；老霍克从备物资发展到安排接应路线。先沿用短局、可重玩的结构，避免简单叠加更多喝酒次数。
- **第一款易接触，后续挑战可选。** 第一次邀请偏重关系进展；高分调酒可以影响对白、纪念物细节或挑战奖励，不必都成为第一款游戏的硬门槛。
- **未解锁提示只透露眼前目标。** 手帐可以提示“下次听他讲完那张样稿”，避免直接展示完整人物结局。当前仍以明确轮数为主，方便测试。

## 6. 验证方式

使用独立 `/tmp` 存档验证，不改玩家的真实进度：

- `tests/run_activity_unlocks.py`：精确章节门槛、最后一句确认、零满意招待、继续下一章、旧存档补齐、两阶段写入失败重试、重启恢复。
- `tests/run_character_activities.py`：三位角色完整章节、正式与演示模式、通关奖励及恢复。
- `tests/run_guest_journal.py`：历史对话、饮酒记录、游戏入口及恢复。
- `tests/verify_story_dialogue.tscn`：当前 233 条剧情路径、21 次来访、身份揭示、选择分支、页面切换恢复及对白显示边界。

测试引擎退出时仍可能报告既有 ObjectDB／资源未释放警告；这些与上述玩法断言应分开记录，不能当作游戏逻辑失败，也不应声称已经修复。

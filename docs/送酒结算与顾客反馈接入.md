# 送酒结算与顾客反馈 v2

## 游戏里的流程

营业期间为当前客人选择酒款，锁定需求、售价和计时起点。配方替换保留原计时起点。
将成品杯拖到送出位置，即视为顾客收到；按锁定售价加金币，确定评分，再返回主页聊天。
送酒后立即在主页显示喝酒反馈。聊天可提前结束，最长三轮，点击回复选项继续。原故事尚未讲完时保留原位置，反馈结束后点「接着听你说」继续故事；本段故事也聊完后才能点「送客，迎接下一位」。
未配置 AI 时自动使用本地口味反馈，正常收款和评分。白天练习不会售出或评分。
凌晨四点停止接待新客人。若当前客人还未送走，时钟停在04:00，继续调酒、结账和点评；送客后结束当天营业并进入次日。
暂停打烊状态与当前客人一起保存，重开游戏仍可继续接待这位客人。没有客人则到04:00直接歇业。
顾客首次介绍前仍显示「？」；反馈不会替故事自动解锁姓名。

## 数据与评分

- `data/guest_mechanics/guest_profiles.json`：基本口味、权重、容差和忌口。小线沿用已确认数值，其他四人的数值注明试玩待确认。
- `visit_events.json`：小线五次故事的临时偏好。入场时锁定，不因为切换页面、重新选酒而变化。
- `settlement_rules.json`：等待期限、超时扣分、星级映射、实际杯感官模型和满意度参数。当前订单保存规则快照，制作后更新配置不会改掉这单的分数。
- `buffs.json`：经典配方的普通风味标签及授权版本。人物的 `buff_affinities` 决定匹配标签加几分。
- 金币：直接收取选酒时的玩家售价。当前版本不额外发小费，也不因低评分自动退款。
- 属性偏差先扣除容差，再求加权平均：`基础分 = clamp(100 - 2 × 加权偏差, 0, 100)`。
- 命中忌口：`rejected`，满意度为空，店铺评价一星；资料缺失或空杯：`data_incomplete`，不创建成功交易、不收钱，保留原杯。含酒限制读取材料的含酒事实，不用“酒感为零”代替无酒精。
- 软状态在同组命中项中取扣分最多的一项，合计最多扣20分。默认超时为选酒后120游戏分钟（现实约两分钟），另外扣10分。旧锁定订单保留原版的合并扣分上限。
- 未舍入分数 >=70 才算满意。星级：90/70/50/30 分对应 5/4/3/2 星，低于30为1星。
- 普通 Buff 仅在真实成品的制作评级为 `perfect`、配方来源和版本有效时激活。匹配人物偏好才加分，重复标签只算一次，合计最多加10分；不匹配的标签仍可展示，但不加分。小线目前偏好清爽+5、气泡+5、杜松+3，完美金汤力的原始13分按上限计10分。总评分在所有加减分完成后限制在0—100，星级最高为五星。旧记录超过100的总评分会在加载时封顶；收款不重复执行。玩家界面只展示总评分、星级与收入，不展示偏好加分数值或计算明细。
- 传说 Buff 尚未启用，《童年拾忆》的配方和奖励字段继续留空。制作质量单独保存，不替代顾客口味评分。主页和评价页以总评分为主要数字，制作质量另存。小线剧情比赛使用固定五段的最终总评分均分，达到60即合格，普通Buff加分计入其中；拒收在剧情门槛中按0分计且占一次。

实际感官值只取最后杯中的原料量，使用共享原料曲线，不取玩家选择的配方名。
当前新订单使用 `sensory-calibrated-1`，以五杯标准配方共同校准。图鉴、工作台、DIY、顾客评价共用一套属性计算；制作质量仍独立评价用量、步骤、用冰与装饰。规则在接待时冻结，旧订单保留其原算法。
糖、杯内固体和装饰品分别处理；装饰不凭空改变酒液甜度，但会参加忌口检查。
未配置的新原料不会按零值处理，须先补感官模型。融冰、温度尚未模拟。

## 开启 DeepSeek

1. 把 `services/customer-feedback-service/.env.example` 复制成同目录 `.env`。
2. 填写 `DEEPSEEK_API_KEY`；`DEEPSEEK_BASE_URL` 默认 `https://api.deepseek.com`，`DEEPSEEK_MODEL` 改成账号可用的聊天模型。
3. 在工程根目录执行：`python3 services/customer-feedback-service/run.py`。
4. 用 Godot 运行游戏并送出酒。服务健康检查：`http://127.0.0.1:8788/health`。

服务启动后每次请求重新读取 `.env`，改密钥不用重启。无需安装额外 Python 包。
只监听本机 8788，与现有图片生成服务的 8787 独立。密钥只放本机服务，已加入 Git 忽略。
朋友拉代码后可直接使用本地反馈；需要 AI 时自己建立 `.env` 并启动服务。
手机或正式发布需要把服务部署到可访问的后端，并设置游戏的反馈地址；开发版本默认本机。

官方接口说明：https://api-docs.deepseek.com/ 。调用 `/chat/completions`，请求 JSON 输出。

## AI 的边界与接口

`POST /feedback`，包含 `request_id`、`round`（1..3）、`guest`、已经听过的 `story`、本段是否讲完的 `story_completed`、
锁定的 `demand`、`drink.actual`、制作质量 `craft`、实际激活的 `buffs`、确定的 `review`、`previous_drink` 和本次 `history/player_reply`。
没有上一杯就不允许“比上次”台词；比较基于实际值。故事只传本次已讲内容，不提前泄露未来章节。
回复 `{ "turn": { "text": "…", "emotion": "pleased", "replies": ["…", "…"], "end": false } }`。
情绪枚举：`pleased/disappointed/thoughtful/neutral`。对白上限220字、选项最多3个、每项50字。
第3轮强制清空选项并结束。非法结构、未配置、超时等情况使用本地反馈。
后端包含四组 few-shot，覆盖吻合需求、与上一杯比较、故事已讲完时道别、故事未讲完时回到原话题。
模型不能更改收入、评分或数值。对白的事实一致性靠输入事实、提示约束和本地兜底，仍需实际试用检查措辞。

## 存档与后续合作

`user://customer_service.json` 保存当前客人、销售记录、评分、反馈轮次、上一杯实际属性。
新记录同时保存感官、满意度、材料含酒事实和 Buff 规则快照、激活与未激活原因、匹配加分明细。旧已结算记录不重算；没有快照的旧锁定订单使用 `settlement_rules_legacy_v1.json` 的原规则，不回溯授予新 Buff。未锁单的旧接待可在锁单前绑定新规则。
`wallet.json.sale_receipts` 独立记录酒款收款，不能复用商店扣款凭据。
结算先保存 intent，再幂等加金币，最后保存评价；中断后恢复同一交易，不重复加钱或评价。
重新开始会备份并清空这些记录。反馈请求绑定客人和交易，送客、结束营业或重开会取消旧请求；到04:00待送客时不取消当前反馈。

调酒模块接入标准：result 必须包含 `drink_id`、`guest.id/visit_id`、`recipe.id`、
`contents.contents`（实际材料→ml）、`contents.solids/garnishes`、`evaluation`。
通过 `CustomerService.prepare_order(recipe_id)` 拿当前 `visit_id`，保存在工作台 guest 中；
成品交付调用 `CustomerService.deliver(result)`。工作台的实际送出动作已经接入这一调用，并在成功后返回主页。新交付必须与 WorkbenchSession 保存的 finished 成品一致；重复提交签名相同的杯子不会再次收钱，修改成品后重试会拒绝。不能用图鉴标准值冒充实际酒液属性。
点评列表和主页总分已读取销售记录。图鉴、研发和实际杯的属性已统一并校准。标准杯满意度预测、推荐排序、评分影响客源/货源和通用传说奖励仍待开发。核对详情见《评分机制核对-20261005.md》。

## 小线剧情衔接（2026-10-05）

销售记录增加 `visit_id`、`visit_serial`、`story_episode_id`、`story_completed`、`cup_signature`。先送酒再讲完故事时，会把已经结账的真实成品与本段绑定。反馈仅收到送酒时已听过的内容，不剧透未讲的故事。随后讲完故事时更新该笔记录的完整已讲内容、身份和章节完成标记。小线固定五段的最终总评分均分≥60时，在第五次反馈与故事都结束后邀请打球。完整规则见《小线羽毛球小游戏-首版接入.md》。

## 送酒后的反馈优先（2026-10-06）

- 成品杯送出并成功结算后立即回主页，显示确定的收入与总评分并请求第一轮反馈。无需先讲完当前故事。
- 未配置密钥、服务未启动、请求超时或返回无效时自动使用本地口味对话，仍有回应选项，最多三轮。不影响已确定的收款与评分。
- 反馈期间点击对话框不会推进原故事，也不能提前送客。反馈结束且原故事尚未完成时，显示「接着听你说」。
- `CustomerService.resume_served_story(delivery_id)` 只接受当前已结算且反馈结束的这笔交易，持久化 `feedback.story_resumed=true` 后恢复原故事位置。切换页面或重启游戏不会吞掉故事、重播已经结束的反馈或重复收款。
- 旧销售存档没有 `story_resumed` 时按 `false` 读取，无需清档。故事结束后显示最终反馈和送客入口；小线剧情门槛仍等待五段故事及对应五杯最终总评分。
- 反馈回调同时检查当前请求实例、交易和待接收轮次。同一轮只提交一次，失败请求的延迟回调不会重复追加对话或覆盖下一轮请求。
- 本地和模型反馈在原故事未完时以回到刚才话题收口，已经讲完才道别；第三轮结束的是这段点评，不会强行结束故事。
- 新成品签名采用 `json-roundtrip-v2`，先规范化 Godot 保存、重读时的数值表示，再对实际材料、步骤等原字段计算签名。重开后同杯重试可以正常确认且不再收款；修改原料或步骤仍拒绝。旧记录保留原签名，接受原格式或新版格式的精确匹配，不回算或迁移历史交易。

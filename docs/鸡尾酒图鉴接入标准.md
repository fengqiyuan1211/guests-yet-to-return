# 鸡尾酒图鉴接入标准

适用于《致未归的客人》当前 Godot 工程。运行时读取 JSON，酒卡文字、数值、标签和步骤由 Godot 排版。酒的图片只画酒本身，不把名称、配方或标签画进图片。

## 1. 文件位置

| 内容 | 工程内路径 | 用途 |
| --- | --- | --- |
| 正式成品酒数据 | `data/cocktails/catalog.json` | 图鉴、详情和酒单使用的酒款定义 |
| 展示补充内容 | `data/cocktails/codex_metadata.json` | 本轮五款酒的故事、步骤文案、器具和卡位，重建数据库时合并 |
| 完整记录例子 | `data/cocktails/cocktail_record.example.json` | 莫吉托的单条记录，便于复制字段结构；不会自动加载 |
| SQLite 对照库 | `data/cocktails/cocktails.sqlite3` | 查询与校对；游戏运行无需 SQLite 插件 |
| 酒款图片 | `assets/art/cocktails/<酒款ID>.png` | 透明底酒杯插画 |
| 图片风格提示词 | `assets/art/cocktails/prompts.json`、`prompts.md` | 后续生成图片时沿用同一风格 |
| 卡片小装饰库 | `assets/codex/decorations/*.svg` | 草本、柑橘、薄荷柑橘与樱桃墨线图案 |
| 器具图标库 | `assets/codex/tools/*.svg` | 详情里的工具与杯型图标 |
| 图鉴设置 | `data/codex_settings.json` | 初始解锁、库存、教程占位和锁定详情访问；现已关闭锁卡详情测试入口 |
| 玩家库存 | `user://supplies_state.json` | 唯一库存、开瓶余量与默认器具状态 |
| 图鉴与酒单存档 | `user://menu_state.json` | 永久点亮列表、来自统一库存的余量快照和已上架酒单 |

Godot 资源路径使用 `res://`，如 `res://assets/art/cocktails/mojito.png`。不要填写某台电脑的桌面绝对路径。

2026-10-01：`allow_locked_details=false`。未点亮酒卡禁用点击，鼠标悬停只提示尚未购买的必需物品；器材、杯型默认拥有，冰和可选装饰不列缺项。买齐必需材料及装饰后永久点亮，才可打开详情。购买与消耗都通过 `Supplies` 同步当前余量；酒谱点亮不会因材料用尽撤销。详情区分「已有」「余量不足」「缺少材料」「已用完」。翻页时收到库存变化，在动画结束后补刷新。

## 2. 正式 JSON 结构

顶层保持 `schema_version: 1`，酒款放在 `cocktails` 数组。当前增加的字段属于 v1 的兼容扩展。

| 字段 | 类型 | 规则与显示位置 |
| --- | --- | --- |
| `id` | 字符串 | 全工程唯一的稳定英文 ID，如 `mojito`。不要因改中文名称而改 ID |
| `name`、`english_name` | 字符串 | 酒卡和详情标题 |
| `type` | 字符串 | `经典` 或 `特调`。右上角分类章根据此字段显示 |
| `image_path` | 字符串 | 透明底 PNG 的 `res://` 路径 |
| `codex_order` | 正整数 | 图鉴顺序；1 号留给新手教程，当前五杯使用 2–6 |
| `decoration_id` | 字符串，可选 | 卡片墨线小装饰，缺失或未识别时回退到 `herbal` |
| `mouthfeel_tags` | 字符串数组 | 口感，例如 `清爽`、`气泡` |
| `flavor_tags` | 字符串数组 | 风味，例如 `薄荷`、`青柠`，详情只显示文字标签 |
| `alcohol_intensity` | 数字 | 酒感，0–100 的独立游戏刻度，不是实际酒精度 |
| `sweetness`、`sourness`、`bitterness` | 数字 | 甜、酸、苦，分别为 0–100，不要求总和为 100 |
| `ingredients` | 对象数组 | 基酒、配料、香草和装饰；不包含任何冰块 |
| `ice` | 对象数组 | 独立的用冰信息，包含冰型、用量、使用阶段与来源 |
| `display_equipment` | 字符串数组 | 详情展示的完整工具列表，不包含杯型 |
| `glass` | 字符串 | 所需杯型，和工具一起展示 |
| `preparation` | 字符串 | 使用箭头概括制作流程，建议不超过 24 字，如 `加冰→加酒→轻搅→装饰` |
| `display_steps` | 对象数组 | 玩家可读的制作步骤，按 `number` 顺序显示 |
| `story` | 字符串 | 这杯酒的故事，使用自然短文，不写操作说明 |
| `story_sources` | 字符串数组，可选 | 故事背景核对链接；保存资料用，不显示为玩家界面内容 |
| `equipment`、`steps` | 数组 | 原工作簿的工具和制作笔记，保留资料来源，便于复核 |
| `source`、`provenance` | 对象，可选 | 原工作表、行号、来源编号等资料信息 |
| `unlock` | 对象，可选 | 原工作簿解锁参考；不等于当前玩家解锁状态 |

`display_steps` 中每项至少有：

```json
{"number": 1, "operation": "准备", "instruction": "准备高球杯、量酒器、轻压棒和吧勺。"}
```

原 `steps` 不覆盖。展示步骤不得擅自增加来源没有确认的时间、摇和秒数或配方数量。当前已去掉玩家不需要的用料行号、试调记录等文案。

## 3. 原料、装饰和用冰

原料项的基本字段为：

```json
{
  "id": "A2-01",
  "sku_id": "sku_white_rum",
  "ingredient_id": "white_rum",
  "name": "白朗姆酒",
  "use": "基酒",
  "amount": 45,
  "unit": "ml",
  "required": true,
  "inventory_unit": "ml",
  "conversion_factor": 1,
  "inventory_amount": 45
}
```

- `sku_id` 与商店、库存连接，必须一致。`ingredient_id` 表示原料种类，`id` 表示这杯酒的一条配方记录。
- `use` 保留来源分类，如 `基酒`、`配料`、`制作香草`、`装饰`。装饰需要反复购买，保留在原料数组中。
- `amount` 必须是数字，不能写成 `45ml`。`unit` 使用 `ml`、`g`、`piece`、`sprig` 或 `dash`；界面再转换为毫升、克、片、块、枝等适合阅读的单位。
- `required=true` 是必需项；`required=false` 是可选项。可选柠檬片仍在配方中显示，但不计入点亮材料进度。
- `inventory_amount` 是按库存单位计算的单杯消耗量。换算尚未确定时使用 `null`，不能填 0。曼哈顿的 1 dash 苦精仍保留未知换算。
- 原料进度以“拥有足够制作一杯的必需原料”为准，库存按 `sku_id` 读取；苦精未确定 dash 换算时只判断有库存，不自行估算毫升。

冰不属于原料。当前用冰写法如下：

```json
{
  "id": "A2-06",
  "name": "碎冰",
  "use": "出品冰",
  "amount": 150,
  "unit": "g",
  "inventory_policy": "excluded_from_ingredient_inventory"
}
```

`制作冰` 用于摇和或搅拌，通常过滤后不留在成品；`出品冰` 留在成品杯中。用冰始终在配方详情和制作步骤中展示，但不进入原料拥有数量、点亮条件或原料库存扣除。冰记录中保留的旧 SKU、换算和库存字段仅用于原表追溯，游戏不要据此当成原料商品。

当前材料进度应为：遗言 `0/4`、莫吉托 `0/7`、金汤力 `0/3`、长岛冰茶 `0/8`、曼哈顿 `0/4`。长岛冰茶另有 1 项可选柠檬片。

## 4. 图片与卡片装饰

酒图使用独立透明底 PNG，现有图片为正方形构图。酒杯完整入画，留出四周空间；图像中不加文字、卡片边框、纸张背景或标签。

每张酒卡由 Godot 的同一个组件绘制：酒图、名称、口感、分类章、未解锁状态和材料进度。牛皮纸、墨线边框、锁图标和角花属于通用 UI，不需要每加一杯酒就重新生成整张卡片。

小装饰由 `decoration_id` 选择可复用的墨线图案，与配方、风味标签分开。当前约定：

| ID | 图案方向 | 当前酒款 |
| --- | --- | --- |
| `default`、缺省或未知值 | 回退到 `herbal.svg` 草本墨线 | 通用默认装饰，无单独 `default.svg` |
| `herbal` | 草本枝叶 | 遗言 |
| `mint_citrus` | 薄荷与柑橘轮廓 | 莫吉托 |
| `citrus` | 柑橘切片轮廓 | 金汤力、长岛冰茶 |
| `cherry` | 樱桃轮廓 | 曼哈顿 |

装饰只点缀卡片边缘，不代替风味标签，不随酒款生成一整张文字图片。当前装饰素材是 `assets/codex/decorations/` 中的可复用 SVG，所需工具和杯型图标放在 `assets/codex/tools/`。卡片的墨线框、锁图案与分类章由共用绘制代码生成。后续修改对应 SVG 就能统一更新同类装饰，无需改酒款 JSON。

## 5. 卡位、解锁与测试设置

当前顺序固定为：

| 卡位 | 内容 |
| --- | --- |
| 1 | 空白，预留给新手教程酒 |
| 2 | 遗言 |
| 3 | 莫吉托 |
| 4 | 金汤力 |
| 5 | 长岛冰茶 |
| 6 | 曼哈顿 |

不为占位创建虚假的酒款 ID、图片或原料。后续加入教程酒时，将它设置为 `codex_order=1`，同时把 `reserved_tutorial_slot` 改为 `false`，让真实教程酒填入 1 号位；保持 `true` 时仍会额外保留空白首位。其他新酒使用唯一递增顺序，超过一页容量后沿用图鉴翻页。当前保留原有至少 3 页图鉴，后面的空页留待新酒填入。

初始设置由 `data/codex_settings.json` 控制：

```json
{
  "reserved_tutorial_slot": true,
  "allow_locked_details": false,
  "initial_unlocked_ids": [],
  "initial_inventory": {}
}
```

新游戏五杯酒全部未解锁，所需原料全部未拥有；器材和杯型默认拥有。`allow_locked_details=false` 已作为当前配置，锁卡不能进入详情，悬停只显示缺少物品。旧版曾开启此开关用于美术验收，现已关闭。购买后的永久点亮和真实余量由 `Supplies` 更新，不修改配方定义。

`initial_unlocked_ids`、`initial_inventory` 只定义新游戏的初始值。已有存档继续读取玩家进度；修改初始设置不会自动覆盖已有玩家存档。希望重新查看全部未解锁状态时，使用游戏设置中的“重新开始”。

运行时通过 `MenuCatalog` 读取玩家状态：

```gdscript
var cocktail = MenuCatalog.get_recipe("mojito")
var progress = MenuCatalog.ingredient_progress(cocktail)
var unlocked = cocktail.unlocked
```

`CocktailDatabase.get_cocktail()` 返回的是酒款定义，不包含当前玩家解锁状态。不要把源表 `unlock.value` 直接用于卡片点亮。

酒单选酒只能来自 `MenuCatalog.unlocked_recipes()`，未解锁酒不能查看详情，也不能加入酒单。

## 6. 酒单价格

当前五款源数据尚未给出市场参考价格。酒单适配接口暂用 `reference_price=1` 作为价格编辑器的初始值，并标记 `price_status=editor_starting_value`。这 1 金币只为方便编辑，不是这杯酒的市场参考价，也不自动代表合理售价；玩家可以自行设价。

后续如果为酒款补充正式 `reference_price`，接口会标记 `price_status=catalog_value`，并将该值作为编辑起点。玩家实际售价保存在已上架酒单项的 `price` 中，不应覆盖酒款定义或用于改变配方。接入价格接受度逻辑时，应区分编辑初始值与经过设计确认的参考价。

## 7. 后续新增一杯酒的流程

1. 确定稳定 ID、中文名、类型和图鉴顺序。复制单条记录例子，保持字段类型一致。
2. 整理非冰原料和装饰，核对商店 SKU、用量和库存单位。另写用冰信息。
3. 写清工具、杯型、制作流程、每一步操作和故事。风味、口感都填文字数组。
4. 沿用提示词风格生成独立酒图，放入 `assets/art/cocktails/`，填写资源路径。
5. 选择已有 `decoration_id`；没有合适图案可暂用 `default`。不要把装饰或文字烘焙进酒图。
6. 把记录加入正式 `catalog.json` 的 `cocktails` 数组，检查没有重复 ID、顺序和原料行 ID。无需为它新建整套 UI。
7. 运行游戏检查酒卡、详情、分页和未解锁状态。新增配方默认不会自动点亮或上架。

本轮数据库由工作目录的 `work/cocktail-database/build_database.py` 从只读 Excel 导出和 `codex_metadata.json` 构建。重建会覆盖 `catalog.json` 与 SQLite，所以若继续使用这条构建流程，配方要先更新数据来源，展示文案要更新 `codex_metadata.json`。直接手工修改正式 JSON 时，应同步维护构建来源，避免下次重建丢失。

SQLite 不会随着手工改 JSON 自动更新。它保留相同完整记录供校对，运行时仍以 JSON 为准。当前 SQL 中有 27 条 `cocktail_ingredients`、5 条 `cocktail_ice`、22 条 `cocktail_steps` 和 5 条 `cocktail_codex_presentation`。

## 8. 接入前检查

- JSON 能解析，`schema_version` 为 1，酒款 ID 不重复，图片资源能加载。
- 1 号位仍为空，五款经典酒位于 2–6，类别章显示“经典”。
- 每条 `ingredients` 都是非冰原料；用冰仅出现在 `ice` 与步骤中。
- 风味标签是文字，卡片小装饰来自统一库。
- 五杯酒在新游戏中均未解锁，材料拥有数为 0；悬停缺项与查看已点亮详情均不改变库存和解锁。
- 详情包含配方、口感、所需器具、制作过程、制作步骤、风味标签和故事。
- 未解锁酒不能上架、不能进入详情；首次买齐必需材料和装饰后开放，材料耗尽不取消点亮。

## 9. 2026-10-04 成品酒图画风更新

五款经典酒更新为细墨线与柔和水彩的手绘插画。仍使用 `assets/art/cocktails/<id>.png`；酒款 ID、JSON schema、卡位和解锁条件均沿用原接口。图片为正方形 RGBA PNG，带真实透明通道，只含完整酒杯及配方装饰，不含文字、纸底或外部投影。Godot 使用 KEEP_ASPECT_CENTERED 等比显示，图鉴未点亮时继续使用原灰度材质；详情和酒单共用相同资源。

生成提示词保存于 `assets/art/cocktails/prompts.json` 和 `prompts.md`。稳定风格编号仍是 `saloon-cocktail-cutout-v1`，追加 `style_revision=handdrawn-watercolor-20261004` 记录此次画风；以后生成请以此修订的模板及已确认图片为准。图片替换无需修改配方 JSON 或 SQLite。保留 PNG 的现有 `.import` UID，Godot 根据源文件变化重新导入；协作时提交 PNG 与提示词文件，不提交 `.godot` 缓存。

### 图鉴酒图的统一排版

`cocktail_art_layout.gd` 在运行时采样 PNG 的可见范围构造 AtlasTexture，排除几乎透明的杂点与外围留白；原图片与 `image_path` 保持完整。卡片酒图区为 `(20,26,132,158)`，详情酒图区为 `(144,113,306,277)`，等比显示并对齐底部，文字区从 x=160 起，角花降低透明度。

图片构图补充文件 `assets/art/cocktails/layout.json` 使用 `schema_version=1`，`cocktails` 按稳定酒款 ID 存放 `body_top` 与 `body_bottom`。两者是原 PNG 高度中的 0–1 归一化坐标，分别标记杯身最高处和杯底，不把突出杯口的薄荷、柑橘算入杯身。公共组件以杯身为尺寸基准，另留出装饰空间；酒图不拉伸、不裁掉装饰。这个文件只控制美术展示，不改配方、库存和点亮数据。未提供构图记录的新酒回退到可见范围等比显示，后续可补这两个坐标。更新图片构图时一起更新该记录。

详情页酒图使用 `centered=true`：整幅插画在展示区垂直居中，水平方向以杯身中心而非突出装饰居中。`layout.json` 的可选 `body_center_x` 是原 PNG 中杯身中轴的归一化横坐标（0–1）。缺省时按整幅可见插画居中。通用组件把最终边界限制在展示区内，保留完整装饰；图鉴列表继续使用底部对齐。

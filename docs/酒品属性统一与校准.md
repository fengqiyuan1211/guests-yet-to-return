# 酒品属性统一与校准

更新日期：2026-10-06。模型版本：`sensory-calibrated-1`。

## 这次解决的问题

原先图鉴直接读取策划值；工作台根据所选配方补正属性；DIY 只求原料平均；顾客评价又乘了一组倍数。相同的配料因此会得到不同属性。旧酸度倍率约 5.33，使遗言和长岛冰茶过早达到上限。

现在四个入口共享 `scripts/sensory_model.gd` 和 `data/sensory/model.json`。算法只读实际用料和冻结的模型，不读玩家给酒取的名字，不根据选择的经典配方抬高或降低实际杯属性。

## 五杯标准校准

顺序为酒感、甜度、酸度、苦度。

| 酒 | 共享模型标准值 | 调整 |
| --- | --- | --- |
| 遗言 | 65 / 45 / 65 / 20 | 保留原策划值，实际杯不再饱和到 100 |
| 莫吉托 | 40 / 35 / 45 / 0 | 保留已确认数值 |
| 金汤力 | 35 / 25 / 20 / 30 | 保留原值，小线基础偏好仍以它为参考 |
| 长岛冰茶 | 55 / 55 / 47 / 10 | 酸度原 45，校准为 47，保留酸度随浓度的变化 |
| 曼哈顿 | 75 / 30 / 10 / 35 | 苦精每 dash 按 1 ml 计算和扣库存 |

主要液体配方没有改动。`reference_attributes` 保留校准前的策划值。四项都是 0–100 的独立游戏感知刻度，不是化学含量或实际酒精百分比。材料实际 ABV 未知时继续保留空值。

## 输入与计算

```gdscript
const Sensory = preload("res://scripts/sensory_model.gd")
var model = Sensory.snapshot()
var result = Sensory.evaluate(
    {"sku_gin_london_dry": 50.0, "sku_tonic_water": 150.0},
    {},
    {},
    model
)
# result.attributes: 35 / 25 / 20 / 30
```

- `contents`：实际出品杯中的液体，数量单位 ml。
- `solids`：实际出品杯中保留的固体，使用物品既有库存单位。
- `definitions`：可选的操作别名到 SKU 的定义。内置兼容金酒、青柠汁等现有别名，同一材料的别名和 SKU 混用会累加。
- `model`：本次制作或订单冻结的完整参数，不能中途换成最新配置。
- 返回 `attributes`、`raw_attributes`、`version`、`volume_ml`、`missing`、`data_complete`。
- 内部使用浮点数；界面显示时可取整，不要先取整再算顾客满意度。

先把每种液体的 ml 乘原料感官系数，固体糖按克数增加甜味贡献，再除以实际酒液体积，最后经过共享的连续分段校准曲线。曲线单调，不再对所有酒统一乘 5.33。加苏打会降低浓度，加青柠会增强酸味，加糖会增强甜味，相同比例的双份酒属性相同。

糖的贡献是游戏近似，不补造溶解率。装饰不当成果汁，冰不计入原料或液体体积；目前没有模拟融冰、温度和香气萃取。搅拌不足等步骤问题仍影响制作质量和 Buff 激活，不再用任意的甜酸苦加数模拟。

空杯、未知原料、负数、无效数字和不完整的标准用量返回 `data_complete=false`。顾客结算会拦截这种数据，不把未知材料当成零属性卖出去。

## 标准配方与图鉴

```gdscript
var standard = Sensory.standard(recipe, model)
```

读取 `ingredient_rows` 或正式配方的 `ingredients` 数组，使用 `inventory_amount` 和 `inventory_unit` 换算，不把装饰或冰加入酒液。`CocktailDatabase` 加载时也按此方式计算标准杯。

新增液体时先在 `data/sensory/model.json` 补感官系数和既有物品 ID，再写标准配方。修改配方后更新保存的标准数据：

```sh
# 在工程目录运行，把 Godot 换成自己的可执行文件位置
Godot --headless --path . --script res://tools/calibrate_cocktails.gd
python3 tools/sync_cocktail_sqlite.py
```

前一个工具直接调用运行时算法，更新 JSON 属性和模型版本；后一个同步现有 SQLite 对照库。游戏实际读取 JSON。`codex_metadata.json` 是展示补充文件，不用于替代共享算法；旧工作簿导出工具也不是新的属性计算入口。

## 制作、评价和旧存档

- 新制作 session 保存 `sensory_model` 和 `quality_model`，完成后的成品也保存模型。
- 新顾客保存完整规则快照。选酒开始制作时，把匹配的顾客模型交给工作台，因此中途调配置不会让这杯酒的出品属性和评价算法错开。
- 顾客总分、口味容差、Buff 加分、超时和忌口仍按既定评分机制计算。小线隐藏剧情仍取五段对应的总评分。
- 已经开始的旧经典制作、旧订单、已有 DIY 成品和历史交易保留原算法或原结果。新版本不会重算已卖出的酒。
- 标准杯满意度预测、推荐排序、评分影响客源和货源尚未实现，此次统一只覆盖四项感官属性及其接入。

## 验证

`tests/verify_sensory_unification.tscn` 会实际购买原料、选酒、制作、出杯并结算五杯，再对比图鉴、工作台、DIY、顾客评价，检查金币只结算一次和保存状态有效。必须使用隔离的临时存档路径运行测试。其他原生验证结果存于本次校准工作目录。

### 0.1 已确认的方向

第一人称调酒、酒馆经营与文字剧情结合的 2D Godot 游戏。美术采用暖色手绘、西部酒馆与海港元素。原料、实际剂量、冰型、技法与流程尽量贴近真实调酒；首版不做真实液体物理。酒款名称使用中英双语。

工作台共用同一套制作系统，通过“营业模式／研发模式”决定是否关联订单、如何展示结果、是否结算收入。标准酒谱与每次实际制作始终分开。

## 1. 两部分分别负责什么

### 1.1 工作台

【已确认】负责“一杯酒怎么被做出来”：选杯、取料、量取、加入、选冰、摇和／搅拌／轻压、过滤、装饰和出杯。选择酒谱后仍可偏离材料、剂量与步骤。

【建议】工作台接受制作上下文，返回单杯记录和结果；不自行修改官方酒谱，不直接推进剧情，不自行决定酒单上架，也不直接写钱包。

### 1.2 研发

【已确认】负责“为什么试调、以哪款酒为起点、如何把做法保存为配方”。主页有独立研发按钮，可有轻量准备页；实际操作复用工作台研发模式。

【已确认】支持以已有酒谱改编或新建 DIY；图鉴详情的“以此研发”进入同一流程。完成后看结果、命名、填写中英文名称或备注，保存到图鉴 DIY 分类。保存不自动上架。

【已确认】传说特调主要通过配方道具解锁，与 DIY 分开。研发资源、次数、保存数量与修改范围需要配置，但未定稿。

### 1.3 玩家主流程

【已确认】主页研发／图鉴以此研发 → 选择基础配方或新建 → 工作台试调 → 查看结果 → 命名保存到图鉴 → 玩家决定是否上架。

【建议】营业流程：有效订单 → 选择目标酒谱 → 同一工作台制作 → 出杯预览 → 确认交付 → 评价与销售结算成功 → 通知主页完成接待。订单完成不由“点击出杯”提前宣告。

## 2. 页面、操作与反馈

### 2.1 工作台布局

| 区域 | 内容与交互 | 状态 |
| --- | --- | --- |
| 左上纸条 | 当前订单要求、目标配方材料、制作步骤；未来多订单可折叠 | 已确认 |
| 中央桌面 | 第一人称杯具、量酒器、制作容器与成品；被选容器描边，动作有倒入、搅动等反馈 | 第一人称已确认；布局和反馈建议 |
| 左／右侧原料区 | 点击或拖动取料，显示余量、计量单位和本次取出量 | 建议 |
| 桌面工具区 | 按当前容器显示量取、加冰、轻压、摇和、搅拌、过滤等可用操作 | 操作已确认；摆放方式建议 |
| 底部操作区 | 显示当前手持工具、实际剂量、计时反馈、返回、丢弃、出杯／结束试调 | 建议 |
| 结果页 | 本杯实际属性、用量、损耗、成本；营业显示评价，研发显示试调分析与保存入口 | 记录内容已确认；呈现方式建议 |

【建议】纸条分“目标”与“实际”两列，使用“目标 20 ml／已加入 18 ml”这类直接反馈。偏离配方是提醒，不阻止继续。禁止操作只用于真实约束，例如库存不足、容器容量不够、工具不适用；不能把偏离经典配方当成操作错误。

【建议】首版只支持一个活动制作会话，切页面保留；折叠订单先保留布局扩展点。选择新订单或新研发时，如有半成品，提供“继续这一杯／丢弃后开始”，不静默覆盖。

### 2.2 研发准备页

【建议】只放四项内容：已有酒谱／新建 DIY、来源配方摘要、当前允许操作的范围、开始试调。若配置了费用或次数，必须在开始前展示准确规则与余额；未配置则显示开发占位说明，不编造价格。

【建议】从图鉴进入时预选来源与版本；从主页进入时自行选择。准备页返回不扣料。是否在开始时消耗研发资源属于待定规则，由策略配置控制。

### 2.3 一次制作的操作步骤

| 步骤 | 玩家操作 | 系统行为与反馈【建议】 |
| --- | --- | --- |
| 1. 开始 | 选目标配方或空白 DIY | 创建独立会话，锁定来源配方版本、数据版本及模式 |
| 2. 选杯与工具 | 选择成品杯、量酒器和制作容器 | 显示容量、适用动作；杯具和工具为可复用物，不按液体扣料 |
| 3. 取料与量取 | 选原料，指定或操作量取 | 显示预计取出量；成功提交后扣库存、加入指定容器并留记录 |
| 4. 加入与转移 | 量酒器倒入摇壶或杯子 | 只搬动本会话已有材料，不再扣库存；显示容器余量与损耗 |
| 5. 冰与技法 | 选冰，轻压、摇和、搅拌 | 记录冰型、数量或质量、顺序、操作时长；即时反馈动作进度 |
| 6. 过滤与装饰 | 选过滤方式，转入成品杯，加装饰 | 记录保留液体、残留及丢弃的冰；装饰按实际消耗单位记录 |
| 7. 出杯 | 确认目标成品容器 | 冻结本杯结果；尚在其他容器的内容单独处理，不能算进成品 |
| 8. 后续 | 营业交付／研发分析保存 | 按模式执行下一步，失败重试沿用同一个请求编号 |

【建议】首版用可调剂量按钮或滑杆完成量取，仍记录实际值；后续替换为按住倾倒、过冲与手部操作，不改底层动作协议。首版摇和／搅拌可以使用简化计时交互，但记录时长，为后续融水与制作表现预留。

【建议】全局“返回”只离开页面，“丢弃”才终止这杯。用词分清“结束试调”和“交付顾客”，避免研发被误解为卖酒。

## 3. 共用系统与模式差异

| 项目 | 营业模式 | 研发模式 |
| --- | --- | --- |
| 容器、动作、计量、冰与技法 | 共用 | 共用 |
| 原料、损耗、成本和单杯记录 | 共用 | 共用 |
| 目标配方 | 固定版本，可自由偏离 | 来源配方固定版本；空白 DIY 可无目标 |
| 顾客订单 | 关联有效订单与接待 ID | 不关联订单 |
| 结果重点 | 配方还原、制作表现、顾客匹配；硬性禁忌优先 | 成品属性、制作情况、成本及与来源差异 |
| 偏离经典 | 影响还原维度，影响大小待定 | 不因此直接判失败 |
| 结束操作 | 交付并进入评价与销售结算 | 看结果，保存配方或不保存 |
| 金币 | 按订单规则结算；金额与拒收政策待定 | 没有销售收入；研发费用待定 |
| 配方写入 | 不自动从本杯生成新配方 | 玩家确认后写 DIY 新配方或新版本 |
| 上架 | 本模块不自动处理 | 保存后仍需玩家去酒单决定 |

前述模式边界为【已确认】；接待 ID、具体按钮及处理顺序为【建议】。

【建议】教学免费练习作为独立资源策略 `practice`，使用虚拟库存、不收款、不产生真实解锁或收益。若需要将教学结果存为 DIY，必须另行确定规则；不能复用正常取消退款逻辑。

## 4. 制作、取消、重做、保存与恢复

### 4.1 状态流程【建议】

制作状态与页面分开：关页面不代表结束制作。

准备中 → 制作中 → 结果已冻结 → 营业：交付待确认 → 已交付

准备中 → 制作中 → 结果已冻结 → 研发：编辑配方草稿 → 保存待确认 → 已保存／不保存结束

制作中 → 暂存离开 → 恢复制作中

制作中／结果已冻结 → 确认丢弃 → 已丢弃

【建议】“暂存离开”是界面状态，不重建会话；“已交付／已丢弃／研发结束”是不可再次制作的终态。编辑草稿独立于冻结的单杯记录，保存失败可重试，不能重新消耗材料。

| 情况 | 处理规则 |
| --- | --- |
| 开始前取消 | 【建议】未取料不扣材料；研发费用是否已消耗按明确配置和已提交凭据判断 |
| 取料后取消／丢弃／失败 | 【已确认】不自动退已用原料；【建议】把容器剩余材料记入废弃，保留历史 |
| 重做 | 【已确认】不自动退原料；【建议】新建会话 ID，关联上一杯 ID，重新取料；费用按配置重新判断 |
| 切换图鉴或主页 | 【已确认】保留半成品；【建议】界面释放，服务和已提交快照保留 |
| 摇酒过程中退出 | 【建议】持续动作划为小段提交，恢复到最近已保存进度；不把离线时间计入摇酒时长 |
| 结果页退出 | 【建议】恢复同一冻结结果，不重复计算随机因素、不重复出杯 |
| 配方保存失败 | 【建议】保留草稿，显示原因，重试相同保存请求；不占第二个名额、不重复扣资源 |
| 收款失败或中断 | 【建议】保留待结算状态，恢复时查询同一结算凭据，不能靠再点一次发新付款 |
| 配方在图鉴被修订 | 【已确认】当前杯继续使用原版本；下次制作再选新版 |
| 04:00 歇业／顾客离开 | 【建议】沿用现有歇业逻辑，保留半成品；旧订单标记失效并禁止向下一位顾客交付；后续丢弃或其他处理由规则决定 |
| 全局重新开始 | 【建议】把新会话、库存、DIY、研发资源、结算凭据纳入统一备份和重置；是否保留 DIY 待定，不默认绕过重置 |

【待定】暂停菜单、切页面时是否继续制作计时或融冰；建议首版仅在工作台主动操作时推进制作计时。营业时钟仍由现有 TimeManager 管理，不能用游戏一分钟直接当作真实摇酒一分钟。

### 4.2 扣料与转移：一份原料只能扣一次

【需求中的建议，建议采用】原料从库存进入制作会话时扣除；会话内从量酒器倒入摇壶属于转移，不再扣库存。

例：取出 18 ml、洒漏 1 ml，库存减少 18 ml、当前容器得到 17 ml、成本计 18 ml。如果这 17 ml 再完整倒入摇壶，库存不变，量酒器减 17 ml、摇壶加 17 ml。这里的“进入容器”不一定等于最终入杯，过滤和后续损耗仍需继续记录。

【建议】每种原料维护守恒关系：

取出总量 = 各容器现存量 + 已装入冻结成品量 + 累计洒漏／残留弃置量。

【建议】冰融水单独从“冰”转为“水”，不凭空增加质量；装饰以件或克计，不能直接与 ml 相加。混合液转移按模型分配各成分，首版可用均匀混合近似；记录其模型版本。固体过滤、碎冰与整冰单独处理，不能全部当作液体同比倒出。

【建议】首版没有溢出模型时，容量不足应在提交前拒绝整次操作且不扣料；后续若支持部分倒入，必须明确记录实际取出、留存和溢出，不可静默截断数量。

### 4.3 防重复与存档一致性【建议】

每个扣料、动作、研发消耗、保存和交付请求都带稳定的 `command_id`。含义是“这一次操作的收据号码”。同一请求重试必须返回原结果；禁用按钮只改善体验，不能替代底层去重。

1. 先检查会话状态、库存、容量及研发权限，确定本次结果。
2. 在候选快照中同时更新库存、容器、动作记录和命令收据；按会话修订号拒绝过期操作。
3. 持久化成功后才向界面报告成功和播放完成反馈；失败则保持旧状态。
4. 保存配方同理：新版本、研发名额／费用与保存收据一起提交；名额满或写入失败不能产生半条配方。
5. 交付跨订单与独立钱包：先持久化交付意图和唯一结算 ID；钱包按 ID 只记账一次；写回收据后完成订单，再通知主页。任何中断都从同一 ID 补完。
6. 底层拒绝同一单杯交给不同订单，拒绝同一订单被重复完成；已冻结的成品不能再次拆开制作。

【建议】首版由统一存档协调器持久化“库存＋制作会话＋研发资源＋DIY 版本＋命令凭据”的同一事务快照。库存服务仍拥有库存业务权限，协调器只负责保存一致性，不让 UI 直接写库存。若团队已建设独立库存存档，则需要事务日志与恢复协议，不能只各自保存一个 JSON 就声称一致。

【建议】保留临时文件、最近有效快照、版本校验与恢复标记；加载有错时保留原文件并停止新扣料，不能默默重置库存。存档的 `schema_version` 与玩法 `model_version` 分开。协调器最终应与 GameSession 的备份、重置、订单恢复顺序对齐。

## 5. 数据对象：不要把四种东西混在一起

| 对象 | 通俗解释 | 谁能改 | 何时产生 |
| --- | --- | --- | --- |
| 标准配方 RecipeVersion | “这款酒打算怎么做”的正式参考 | 官方版本由内容维护者发布；玩家不能覆盖 | 内容发布／DIY 保存 |
| 制作会话 BrewingSession | 正在桌上制作的这一杯 | 制作服务通过动作修改 | 开始制作 |
| 单杯记录 DrinkRecord | “这一杯实际上发生了什么”的完整记录 | 冻结前由制作服务累积；冻结后不可改 | 会话结束或成品冻结 |
| 配方草稿 RecipeDraft | 玩家准备保存的可复现做法 | 玩家在保存前编辑 | 研发准备／试调结果转草稿 |

【建议】配方身份 `recipe_id` 表示同一款酒；配方版本 `recipe_version_id` 表示某次明确做法。新版本不覆盖旧版本。制作会话和单杯记录各自有独立 ID。

### 5.1 所需数据集与关键字段【建议】

| 数据集 | 关键字段 | 主要读写方 |
| --- | --- | --- |
| 原料定义 IngredientDefinition | `ingredient_id`、双语名、液体／固体类型、计量单位、酒精信息、四维属性模型输入、风味、口感、禁忌线索、来源版本 | 内容维护写；库存、制作、评价读 |
| 冰型 IceDefinition | `ice_id`、形状／类别、质量单位、模型参数引用；参数值待定 | 内容维护写；制作计算读 |
| 工具／容器 EquipmentDefinition | `equipment_id`、类型、容量、允许技法、可复用标记 | 内容维护写；操作校验读 |
| 库存与成本 InventoryLot | `lot_id`、原料 ID、可用数量、单位、单位成本、成本版本 | 库存服务写；制作申请取出；单杯固化成本快照 |
| 配方 RecipeVersion | ID、版本 ID、官方／DIY／传说类型、双语名、来源配方版本、材料计划、容器、冰、步骤、目标属性、说明、发布状态 | 官方导入／DIY 服务写；图鉴、工作台读 |
| 研发草稿 RecipeDraft | `draft_id`、基础版本、期望用量、期望步骤、双语名、备注、来源单杯 ID、草稿修订号 | 研发界面经服务写 |
| 制作会话 BrewingSession | `session_id`、模式、订单与接待 ID、目标版本快照、容器、累计取料与损耗、动作序号、状态、模型版本、研发凭据 | 制作服务写；工作台、存档读 |
| 动作 ActionRecord | `command_id`、序号、动作类型、原料、源／目标容器、请求量、实际量、损耗量、时长、冰变化、操作结果 | 制作服务追加；结果分析读 |
| 单杯 DrinkRecord | `drink_id`、会话 ID、目标版本、实际用料、顺序、时长、冰、损耗、成品数量、实际属性、成本明细、评价、计算版本 | 冻结生成；评价、研发、历史读取 |
| 研发策略 ResearchPolicy | 灵感／试调／保存费用、计费触发点、次数、保存配额、修改范围、重做规则、教学例外、策略版本 | 配置维护写；研发资格与消耗服务读 |
| 订单快照 OrderContext | `order_id`、`visit_id`、目标版本、需求、硬性禁忌、报价快照、有效状态 | 订单系统写；工作台读；交付协调器校验 |
| 事务凭据 CommandReceipt | 命令 ID、操作类型、实体 ID、结果、修订号、结算状态 | 协调服务写；重试与恢复读取 |

【建议】液体、质量和件数分别使用统一基础单位；持久化用整数最小单位并在 UI 转换显示，具体精度待定。不同单位只在存在明确换算数据时转换。成本以取出时的单位成本快照计算，不因之后进货涨价而改写历史。

【建议】未定策略使用明确的 `unconfigured` 状态，区别于免费、零次、无限制。开发测试可用显式测试策略，但不能将测试值当作正式平衡数值。修改范围应区分“允许试调什么”和“允许保存成什么”，不能无提示剥夺已确认的工作台自由度。

### 5.2 读写关系【建议】

内容数据 → 配方服务 → 图鉴详情／研发准备 → 会话中的固定配方快照。

库存服务 → 取料事务 → 容器与动作记录 → 冻结单杯 → 属性／成本／评价结果。

单杯结果 → 玩家整理的配方草稿 → DIY 新配方／新版本 → 图鉴 DIY 分类。

图鉴已保存配方 → 酒单选择 → 玩家确认上架。工作台与研发都不直接写上架列表。

订单系统 → 订单快照 → 营业会话 → 交付协调器 → 钱包收据／订单完成 → 主页表现。

### 5.3 从单杯提炼可复现配方【建议】

结果页同时显示“实际做了什么”和“准备保存什么”。初步提取材料、有效加入量、冰型、技法顺序、目标时长、杯型和装饰，排除洒漏、误拿、取消、重复点击等偶然事件，但不自动抹掉玩家有意的改编。

例如取出 18 ml、洒漏 1 ml 后加入 17 ml：本杯成本永远按 18 ml；保存页允许玩家选择期望下次准确加入 17 ml，或把目标修正为 18 ml。这里没有唯一可自动猜对的答案。

过滤、去冰、弃去残渣等可能是正常工艺，不应与洒漏一并删除；草稿可记录必要工艺步骤与预期产量，但不能要求玩家下次故意洒漏来复现。

草稿保存前显示差异摘要：材料／剂量、步骤、冰、时长、目标产量、名称。草稿若与本杯做法不同，其属性只能标成“预估／待试调”，不能直接继承本杯实测结果作为已验证属性。是否要求重新试调才能保存或上架为【待定】。

### 5.4 另存与修订【建议】

- 从官方／传说酒谱改编：仅创建新的 DIY `recipe_id`，记录来源，不能修改原酒谱，也不能获得传说道具解锁标记。
- 另存为新配方：新身份、新首版本；消耗新增名额与否按配额策略。
- 修订已有 DIY：保留身份，新增不可变版本；旧杯与旧订单仍引用旧版。
- 如该 DIY 已上架：不悄悄替换当前酒单或已接受订单的版本；提示玩家到酒单确认使用新版。版本切换政策需与酒单负责人确定。
- 保存成功后显示“已存入图鉴”，提供“查看配方”和“去酒单”；后者只导航，不自动上架。

## 6. 成品属性、成本与评价

### 6.1 不能混用的数据【已确认】

- 目标属性与实际成品属性分开。
- 基础四维为酒感、甜度、酸度、苦度，暂用 0—100；酒感不是 ABV。
- 风味、口感、禁忌线索、剧情标签与特殊 Buff 分开存储与处理。
- 营业评价分配方还原、制作表现、顾客匹配；硬性禁忌先判断。
- 研发不因偏离经典直接失败。评分系数、融水模型、研发费用和 Buff 未定。

### 6.2 计算链与展示【建议】

实际材料／各成分留存量＋有效操作／时长＋冰与融水 → 成品描述与四维 → 按模式进行解释或评价。

【建议】不要把四维直接当作按体积平均的定稿公式。先定义可替换的计算器，输入完整实际记录，输出四维、风味、口感、禁忌线索、产量及计算版本；数值模型另行校准。ABV 若实现，作为独立可选字段，数据不足时显示未计算，不能拿酒感代填。

【建议】先给分项结果和原因，不急于合成一个总分。硬性禁忌命中返回明确标记，顾客匹配不能被其他高分抵消；是否拒收、是否退款和金币结算规则待定。禁忌线索从实际材料和工艺数据传递，不能只看酒名或目标配方。

【建议】研发结果分“能否形成可记录成品”“操作是否存在问题”“味道与结构如何”，配方对比只是分析。容器为空、数据非法属于无法出杯，不等于创新失败。

【建议】本杯原料成本 = 各材料实际取出量 × 取出时单位成本之和；包含洒漏、丢弃及实际消耗的装饰。研发资源费单列，工具折旧、冰和其他耗材是否计价待定。成品留存成本可供分析，但不能用它替代实际支出。

【建议】剧情标签只能由内容规则授予；Buff 先保留数据扩展点，不按某个风味词自动产生奖励或剧情解锁。

## 7. 必要的跨模块接口【建议；以下为拟定契约，不是现有 API】

| 对接方 | 工作台／研发请求或事件 | 必须保证 |
| --- | --- | --- |
| 库存 | `withdraw(session_id, command_id, ingredient_id, quantity, unit, revision)` | 返回实际扣除、批次成本和凭据；与容器更新同事务；不足不部分静默扣除 |
| 图鉴／配方 | `get_recipe_version(id, version)`、`save_diy(draft, request_id, expected_revision)` | 读取不可变版本；保存返回身份与版本；官方只读；去重 |
| 图鉴入口 | `research_requested(recipe_id, version_id)` | 与主页创建相同类型的研发上下文 |
| 订单 | `get_order_context(order_id)`、`validate_delivery(order_id, visit_id, drink_id)` | 校验有效接待、订单状态与硬性需求，不绑定“当前显示的客人”猜测归属 |
| 交付／钱包 | `deliver(delivery_id, order_id, drink_id)`；钱包按 `delivery_id` 记收入 | 只结算一次；返回评价与持久化收据，之后才通知主页 |
| 酒单 | `list_publishable_recipes()`、`request_menu_edit(recipe_id, version_id)` | 用户确认才上架；报价、上架版本独立于工作台 |
| 研发资源 | `authorize_research(context)`、按命令 ID 提交策略规定消耗 | 在规定节点一次消耗；失败重试不重复收费 |
| 存档 | `capture_brewing_state()`、`restore_brewing_state(snapshot)` | 会话、库存、研发与命令记录一致，加载后不重复执行历史动作 |

【建议】先与库存、图鉴和订单负责人确认 ID、单位、版本与事务归属，再各自实现页面。没完成的外部系统先用可替换的测试适配器；测试订单、虚拟库存必须明确标识，不能冒充营业系统已完成。

【建议】当前 `MenuCatalog` 以 `id` 管理解锁与酒单，缺少制作步骤和明确版本绑定。新增配方服务作为制作数据权威来源，给现有酒单提供展示适配层；不要在 `MenuCatalog` 与新服务各维护一套可独立改写的正式配方。

## 8. Godot 场景与服务划分【建议】

### 8.1 场景

- `research_prepare.tscn`：选择基础配方／新建、费用与限制说明、开始试调。

- `recipe_save_panel.tscn`：双语名称、备注、差异确认、另存／修订。

这些是拟议新增文件，本次没有创建游戏场景。图鉴 DIY 分类和详情在既有图鉴上扩展，不复制一个图鉴。

## 9. 首版范围与开发顺序【建议】

### 9.1 首版应覆盖

- 一次一个会话；一个共用工作台的营业与研发模式。
- 选杯、剂量取料、容器转移、选冰、轻压、摇和、搅拌、过滤、装饰、出杯的离散操作。
- 固定配方版本与自由偏离；液体和非液体单位分开。
- 实际取出、留存、损耗与成本记录；取消不退款，重做新会话。
- 单杯冻结、研发结果、草稿整理、双语保存、另存与修订、图鉴 DIY 读取。
- 去重、库存一致性、切页面与重启恢复。
- 营业接口闭环可先用测试订单／钱包适配器验证；正式发售前必须接真实订单和收款。

### 9.2 后续扩展

- 连续倾倒、多倒少倒的操作表现与误差。
- 更细的摇酒时间、冷却与融水影响；首版保留字段和替换点，不宣称模拟真实物理。
- 多订单折叠、并行多杯、多容器复杂工艺。
- 正式评分与经济平衡、灵感费用、次数、Buff 和传奇配方道具内容。

### 9.3 可直接拆成开发任务

| 阶段／任务 | 产出 | 前置条件与验收重点 |
| --- | --- | --- |
| P0-1 数据对齐 | 名称对照表、字段表、单位规范、来源记录 | 确认 Last Word 故事身份；A2 技术表尚待提供与审核 |
| P0-2 接口对齐 | 库存／图鉴／订单／钱包契约与职责表 | 约定版本、ID、事务与时间边界；不等其他 UI 完成 |
| P1-1 无界面制作核心 | 会话、容器、取料、转移、损耗、成本 | 先验证 18／1／17 例子、库存不足和去重 |
| P1-2 存档闭环 | 一致快照、命令凭据、恢复和重置方案 | 中断后物料与记录一致，重复恢复不扣第二次 |
| P2-1 研发工作台 | 准备页＋共用操作界面＋结果页 | 使用明确的测试数据走通空白／改编试调 |
| P2-2 全技法动作 | 冰、轻压、摇和、搅拌、过滤、装饰 | 顺序与时长被记录；非法工具组合有反馈 |
| P3-1 DIY 配方闭环 | 草稿提炼、双语名、另存／修订、图鉴读取 | 不把洒漏固化为做法，不覆盖官方，不自动上架 |
| P3-2 研发策略配置 | 费用／次数／名额／范围的策略接口 | 使用明确测试策略验证限制与去重；正式数值仍待定 |
| P4-1 营业模式 | 订单上下文、评价分项、交付协调器 | 研发零销售收入；失效订单不可交付；一次收款 |
| P4-2 正式系统联调 | 对接库存、钱包、图鉴、酒单及歇业 | 从主页进入到完成接待全流程一致 |
| P5 内容与体验 | 故事首杯、审核后 A2、动画音效与排版 | 技术样例不替代故事内容；完成中断与错误回归 |

【建议】你的第一份可运行成果应是“用测试原料做一杯 → 得到真实记录 → 保存成 DIY → 从图鉴再次制作”，而不是先画完所有页面。并行保留营业上下文字段，后接订单无需再做第二套工作台。

【建议】研发负责人主导会话、动作、结果、草稿与保存界面；库存负责人提供材料与扣料权威，图鉴负责人提供版本展示与入口，订单／钱包负责人提供交付结算。若由一人实现，也应保持这些边界。

## 10. 验收条件【建议】

| 编号 | 操作／情景 | 通过条件 |
| --- | --- | --- |
| A01 | 同一配方从营业与研发进入 | 相同操作生成一致制作记录；仅订单与结算行为不同 |
| A02 | 选择配方后改材料、剂量或顺序 | 能继续制作，目标版本不变，实际记录如实反映 |
| A03 | 取 18 ml、漏 1 ml、再转移 | 库存只减 18 ml，容器累计有效留存 17 ml，成本按 18 ml；转移不二次扣料 |
| A04 | 容量不够／库存不足 | 明确拒绝，库存、容器和成功动作记录不部分更新 |
| A05 | 丢弃后重做 | 原杯消耗保留，新杯新 ID；重复确认不重复丢弃／收费 |
| A06 | 连点取料／重复发送同一命令 | 同一命令只一次生效；有意第二次操作用新命令，可正常增加 |
| A07 | 扣料写盘前后分别强制退出 | 恢复到完整提交前或提交后状态，没有仅扣库存、无材料的半笔账 |
| A08 | 切页、退出并恢复半成品 | 容器、目标版本、动作序号、成本和损耗一致；离线不产生额外摇酒时间 |
| A09 | 制作期间修订 DIY | 当前杯用旧版，新开杯可选新版；历史记录可追溯 |
| A10 | 从有洒漏的试调保存 | 本杯损耗不被改写；保存页可选择期望剂量，不保存偶然洒漏动作 |
| A11 | 双击保存／保存失败重试 | 只有一个目标配方版本，资源及配额只占一次，失败草稿可恢复 |
| A12 | 修订官方／另存 DIY | 官方不可覆盖；另存创建身份，修订生成版本，不偷偷更换已接订单 |
| A13 | 保存后检查酒单 | DIY 可在图鉴查到，酒单没有自动新增 |
| A14 | 顾客硬性禁忌命中 | 禁忌结果先返回且不可被高还原分抵消；具体结算采用配置规则 |
| A15 | 研发偏离经典 | 展示差异与实际结果，不仅因偏离判失败，不产生收入 |
| A16 | 收款前后退出／重复交付 | 同一杯同一订单最多一笔收入；未完成事务可恢复，未完成不换客人 |
| A17 | 04:00 歇业／手动换客人 | 半成品保留，旧订单不能向新客人交付或继续收款 |

# 游戏正在使用的故事对白

这里是已经接入 Godot 的 v0.2 连续故事，后续请直接修改这里的 JSON。`output/` 中的草案与 HTML 试玩是历史审稿材料，不是游戏读取来源。

| 目录 | 客人 | 来访内容 |
| --- | --- | --- |
| `milo/01.json` 至 `05.json` | 米洛 | 地图与勘误 |
| `ada/01.json` 至 `05.json` | 艾达 | 牧场与自己的生活 |
| `hank/01.json` 至 `05.json` | 老霍克 | 风沙救援与被漏掉的人 |
| `stick/01.json` 至 `05.json` | 小线 | 小游戏演员与很久没来的观众 |
| `yellow_creature/repeat.json` | 黄色生物 | 固定两句梗，重复使用 |

`manifest.json` 按来访顺序登记文件，`file` 相对于本目录。共 20 段故事和 1 个固定梗，每位普通客人的五段合成一条连续故事。小线已更新为 v0.3 改稿，其余角色沿用 v0.2。

首次见面的招呼、询问称呼和自我介绍在 `../guest_introductions.json`。播放器把它们接在第一章前，显示自我介绍时记录 `known: true`；在此之前，姓名、称号、右侧介绍以及底部状态均不透露身份。黄色生物在回应固定梗后点亮身份，不额外添加台词。认识状态保存在同一剧情存档中，旧版已有剧情记录的角色视为已认识。

## 修改对白

- `nodes` 是对话节点，`entry` 指定开场。
- `text` 是客人说的话；`choices[].text` 是调酒师的回应，选后跳到对应的 `next`，不能把两条分支同时显示。
- 没有选项但有 `next` 时，玩家点击对白框继续，底部中央显示倒三角。出现选项时只能通过选项继续。
- 收尾节点的 `transition: resume_existing_dialogue_loop` 在玩家点击对白框确认收尾后记录本章完成。下次该客人来访才讲下一章。
- 故事讲完客人留在店里，「再聊一句」读取 `../guest_smalltalk.json`；送客或 04:00 歇业才结束接待。
- 黄色生物只说「我是奶龙」，回应只有「我才是奶龙」，不添加其他对白。
- `guest_id`、章节 `id`、节点名和选项 `id` 用于存档，已发布后不要随意改名。
- 小线的自然语言点单线索已按确认稿加入，并用 `[b]…[/b]` 加粗；它们不直接运行评分或订单判定。其他数值和特殊剧情等待后续系统接入。

## 运行接口与存档

`StoryDialogue` 自动加载器负责分支、闲聊和独立角色进度，`home.gd` 负责展示。节点改变时触发 `changed`；章节确认收尾后触发 `story_finished`。`smalltalk_requested` 预留给后续 AI，当前使用本地闲聊文本。

进度同时记录在 `user://story_progress.json` 兼容记录和 `user://game_session.json` 营业快照。启动时以营业快照为准，将剧情与天数、时间、当前客人一起恢复；钱包仍单独保存。每次回应都会保存，重开程序从当前接待的台词继续；送客或歇业后，该角色下次来访继续未完成的部分。已进入闲聊时重开仍停留在闲聊，不会提前开始下一章。切换功能页不会重新开讲。

从头试玩请点主页左上角原有星形图标 → 重新开始 → 确认重新开始。此操作同时重置营业、剧情、人物相识和钱包，避免只删一个文件造成进度不一致。

工作台已接入真实出杯与结算。新订单通过 `CustomerService.deliver()` 交付，完成反馈与本章对话后由主页 `on_drink_served()` 送客。导出正式包时需要在导出预设的非资源文件包含规则中加入 `*.json`。

## 手帐接入（2026-10-08）

主页左侧原“评价”入口改为“手帐”（`journal` 路由）；鸡尾酒“图鉴”（`codex`）保留。页面使用现有角色立绘、纸张、字体和成品酒液绘制，入口文件为 `scripts/guest_journal.gd`；读取逻辑集中在 `scripts/guest_journal_data.gd`。

### 对话与身份

- 仍以 `StoryDialogue.is_known(guest_id)` 控制身份显示。未相识不显示姓名、资料、偏好或对白。
- 每次实际显示台词／选中回应时追加 `progress[guest_id].archive`；闲聊也保存。
- 去重键为 `chapter_id + speaker + node/choice_id`。重复打开、循环闲聊不会重复收录；不同分支各自保留，不用全文相同来删除不同语境的对白。
- 查询合并旧 `heard`、未结束的 `pending.history` 和新 `archive`，只读已观察内容；不会扫描剧情节点补出未选择的分支。
- 旧版未曾保存的闲聊无法凭空补回。后续重新聊到时会收录。
- 新字段可缺省，沿用版本 1 剧情及营业存档；“重新开始”按现有备份／重置规则清空。浏览手帐不推进故事、不消耗物料、不操作钱包。

### 每杯记录与结算边界

- 从 `WorkbenchSession.state.history` 和当前 `session` 合并读取：只选指定客人关联的 `finished` 成品，排除研发、丢弃和半成品；以 `result.drink_id` 去重。同款酒做多杯仍保留多条记录。
- 酒名、英文名、杯型、颜色、实际属性、工艺品质、原料和冰读取当杯结果快照，不按当前酒谱重新计算。
- 新成品增加 `result.completed_at = {day, minute}`；旧杯回退显示原客人记录的天数，不编造时刻。
- 工作台冻结成品后，经 `CustomerService.deliver()` 结算新订单；已锁定旧订单仍走 `GuestService` 兼容路径。手帐只展示事实，不发钱。新订单硬性禁忌拒收为 0 金币；旧记录保留原实付。
- 旧订单兼容路径在**真正的交付与收款服务成功后**调用 `WorkbenchSession.record_guest_settlement(drink_id, receipt)` 保存不可变凭据。此函数仅保存事实，不生成满意度、不发钱、不替代交付事务。现有 `sales` 字段不由手帐修改。

凭据格式：

```json
{
  "id": "authoritative-payment-id",
  "delivered": true,
  "paid": true,
  "satisfaction": "很满意",
  "score": 92,
  "base_paid": 70,
  "tip": 10,
  "total_paid": 80
}
```

以上数字仅演示字段。`score` 为 0—100；付款须为非负整数且总额等于酒款加小费。重复相同凭据返回成功；冲突覆盖、跨杯复用凭据及不完整数据会拒绝；落盘失败不改变内存记录。结算调用方需持久化自身支付事务，按稳定凭据 ID 重试，不能先写“已支付”再尝试收钱。

### 专属小游戏

`data/guest_activities.json` 以客人 ID → 活动 ID 配置名称、说明及 `route`。米洛、艾达、老霍克由 `GuestActivities.reconcile()` 根据各小游戏条件保存正式邀请，再调用 `StoryDialogue.unlock_activity(guest_id, activity_id, source_event)` 同步手帐；重复调用不重复奖励，手帐写入失败可以重试。

小线登记为 `stick_minigame`，路由为正式 `stick_badminton`。手帐统一进入练习模式，不发剧情奖励；酒馆中的正式邀请由 `CustomerService.memory_summary()` 判断五章完成及五杯评分，首通奖励走正式控制器。内测时保留 `demo_unlocked`，未相识也能体验，身份资料仍受相识进度限制。

当前正式邀请条件：

| 客人 | 完成剧情轮数 | 额外满意招待 |
| --- | --- | --- |
| 米洛 | 2 | 0 |
| 老霍克 | 3 | 0 |
| 艾达 | 5 | 2 |

“完成一轮”指读完该章，包括最后的口味提示并确认继续；不是计算倒过多少杯酒。米洛、老霍克仍有完整 5 轮剧情，解锁小游戏不会跳过后续剧情。旧存档达到条件会自动补齐邀请，不重置已读节点、不重复发首通奖励。章节与节点 ID 保持不变。

米洛、艾达、老霍克复用各自角色小游戏与 `GuestActivities` 奖励记录。新旧两种结算的满意招待都可计入正式邀请，自由调酒订单不冒充剧情招待。手帐练习与正式首次通关分开，不重复领奖。

04:00 由 `TimeManager.closing_pending` 统一保留最后一位客人，完成对话与饮后反馈、送客后才收工；恢复旧版打烊存档时会迁移暂停状态，保留半杯酒和已扣库存。

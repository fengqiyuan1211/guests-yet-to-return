`manifest.json` 按来访顺序登记文件，`file` 相对于本目录。共 20 段故事和 1 个固定梗，每位普通客人的五段合成一条连续故事。文本沿用用户确认的 v0.2 内容。

首次见面的招呼、询问称呼和自我介绍在 `../guest_introductions.json`。播放器把它们接在第一章前，显示自我介绍时记录 `known: true`；在此之前，姓名、称号、右侧介绍以及底部状态均不透露身份。黄色生物在回应固定梗后点亮身份，不额外添加台词。认识状态保存在同一剧情存档中，旧版已有剧情记录的角色视为已认识。

## 修改对白

- `nodes` 是对话节点，`entry` 指定开场。
- `text` 是客人说的话；`choices[].text` 是调酒师的回应，选后跳到对应的 `next`，不能把两条分支同时显示。
- 没有选项但有 `next` 时，玩家点「接着听」继续。
- 收尾节点的 `transition: resume_existing_dialogue_loop` 在玩家点「先聊到这」后记录本章完成。下次该客人来访才讲下一章。
- 故事讲完客人留在店里，「再聊一句」读取 `../guest_smalltalk.json`；送客或 04:00 歇业才结束接待。
- 黄色生物只说「我是奶龙」，回应只有「我才是奶龙」，不添加其他对白。
- `guest_id`、章节 `id`、节点名和选项 `id` 用于存档，已发布后不要随意改名。
- 不在故事文件中加入订单、价格、口味或酒单。这部分等待后续订单与 AI 系统接入。

## 运行接口与存档

`StoryDialogue` 自动加载器负责分支、闲聊和独立角色进度，`home.gd` 负责展示。节点改变时触发 `changed`；章节确认收尾后触发 `story_finished`。`smalltalk_requested` 预留给后续 AI，当前使用本地闲聊文本。

进度同时记录在 `user://story_progress.json` 兼容记录和 `user://game_session.json` 营业快照。启动时以营业快照为准，将剧情与天数、时间、当前客人一起恢复；钱包仍单独保存。每次回应都会保存，重开程序从当前接待的台词继续；送客或歇业后，该角色下次来访继续未完成的部分。已进入闲聊时重开仍停留在闲聊，不会提前开始下一章。切换功能页不会重新开讲。

从头试玩请点主页左上角原有星形图标 → 重新开始 → 确认重新开始。此操作同时重置营业、剧情、人物相识和钱包，避免只删一个文件造成进度不一致。

将来的调酒工作台出杯后可调用主页 `on_drink_served()`。目前调酒台仍是预览页，试玩时用「送客，迎接下一位」。导出正式包时需要在导出预设的非资源文件包含规则中加入 `*.json`。

## 手帐接入（2026-10-08）

主页左侧原“评价”入口改为“手帐”（`journal` 路由）；鸡尾酒“图鉴”（`codex`）保留。页面使用现有角色立绘、纸张、字体和成品酒液绘制，入口文件为 `scripts/guest_journal.gd`；读取逻辑集中在 `scripts/guest_journal_data.gd`。

### 对话与身份

- 仍以 `StoryDialogue.is_known(guest_id)` 控制身份显示。未相识不显示姓名、资料、偏好或对白。
- 每次实际显示台词／选中回应时追加 `progress[guest_id].archive`；闲聊也保存。
- 去重键为 `chapter_id + speaker + node/choice_id`。重复打开、循环闲聊不会重复收录；不同分支各自保留，不用全文相同来删除不同语境的对白。
- 查询合并旧 `heard`、未结束的 `pending.history` 和新 `archive`，只读已观察内容；不会扫描剧情节点补出未选择的分支。
- 旧版未曾保存的闲聊无法凭空补回。后续重新聊到时会收录。
- 新字段可缺省，沿用版本 1 剧情及营业存档；“重新开始”按现有备份／重置规则清空。浏览手帐不推进故事、不消耗物料、不操作钱包。

### 每杯记录与结算边界

- 从 `WorkbenchSession.state.history` 和当前 `session` 合并读取：只选指定客人关联的 `finished` 成品，排除研发、丢弃和半成品；以 `result.drink_id` 去重。同款酒做多杯仍保留多条记录。
- 酒名、英文名、杯型、颜色、实际属性、工艺品质、原料和冰读取当杯结果快照，不按当前酒谱重新计算。
- 新成品增加 `result.completed_at = {day, minute}`；旧杯回退显示原客人记录的天数，不编造时刻。
- 工作台完成制作后仍为`未交付`；2026-10-09已接入GuestService交付及收款。只有交付事务完成后才显示真实客人评分、付款和小费；拒收显示未收费，不混入工艺分。旧杯不会自动追补消费记录。
- 外部**真正的交付与收款服务成功后**，调用 `WorkbenchSession.record_guest_settlement(drink_id, receipt)` 保存不可变凭据。此函数仅保存事实，不生成满意度、不发钱、不替代交付事务。现有 `sales` 字段不由手帐修改。

凭据格式：

```json
{
  "id": "authoritative-payment-id",
  "delivered": true,
  "paid": true,
  "satisfaction": "很满意",
  "score": 92,
  "base_paid": 70,
  "tip": 10,
  "total_paid": 80
}
```

以上数字仅演示字段。`score` 为 0—100；付款须为非负整数且总额等于酒款加小费。重复相同凭据返回成功；冲突覆盖、跨杯复用凭据及不完整数据会拒绝；落盘失败不改变内存记录。结算调用方需持久化自身支付事务，按稳定凭据 ID 重试，不能先写“已支付”再尝试收钱。

### 专属小游戏

`data/guest_activities.json` 以客人 ID → 活动 ID 配置名称、说明及 `route`。只有剧情奖励明确调用 `StoryDialogue.unlock_activity(guest_id, activity_id, source_event)` 才解锁，重复调用不重复奖励；解锁保存失败会回滚。

小线登记为 `stick_minigame`，已复用本地 `fengqiyuan` 分支的《童年拾忆》羽毛球模型、球场绘制与结果校验，接入独立 `stick_demo` 演示场景。原正式剧情奖励控制器不接入。

- `demo_unlocked: true` 是内测开关；未相识也能从“手帐 → 小线·演示”进入。正式身份资料仍受相识进度限制。
- 手帐与游戏内的“开始游戏”悬停显示“内测演示”，不写入正式活动解锁、不发奖励、不推进剧情。
- 演示期间暂停营业时间，返回手帐恢复进入前的暂停／运行状态，并定位到小线的小游戏页。
- 正式接入时关闭 `demo_unlocked`，在确定的剧情节点调用 `StoryDialogue.unlock_activity(guest_id, activity_id, source_event)`；剧情奖励、配方和结算另行接入正式控制器。
